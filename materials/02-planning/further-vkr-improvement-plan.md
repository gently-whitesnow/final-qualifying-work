# План дальнейшего улучшения ВКР

Документ фиксирует следующий рабочий проход после текущего черновика ВКР и отчета по преддипломной практике. Цель прохода — превратить уже собранную доказательную базу в более сильную итоговую работу: с аккуратной теорией, расширенными испытаниями, выверенной библиографией и материалами для защиты.

## 1. Методическое выравнивание текста

1. Проверить структуру ВКР по требованиям кафедры: титульный лист, задание, реферат, содержание, перечень сокращений, введение, главы, заключение, источники и приложения.
2. Уточнить формулировки объекта, предмета, цели и задач так, чтобы они не расходились между введением, заключением и презентацией.
3. Убрать из основного текста лишние локальные пути и оставить их только там, где они нужны как воспроизводимые команды стенда.
4. Пройти по тексту на предмет повторов: особенно в главах 2-4, где описание SignalR, Redis backplane и стенда может дублироваться.
5. Синхронизировать содержание с фактической версткой после финальной сборки DOCX.

## 2. Усиление теоретической главы

1. Расширить сравнение подходов к масштабированию: sticky sessions, Redis backplane, message broker/event bus, managed real-time service.
2. Для каждого подхода явно указать, какое свойство он решает: балансировку подключения, межузловую доставку, отказоустойчивость, наблюдаемость.
3. Пронумеровать подходы в таблице и ссылаться в тексте на номер подхода, чтобы не возникало расхождения между названием в таблице и формулировкой в абзаце.
4. Развернуть аргументацию выбора Redis backplane для SignalR: показать, почему он подходит для self-hosted стенда, почему не выбран только sticky sessions и почему полноценный broker/event bus был бы избыточен для текущего этапа.
5. Добавить 2-3 связующих абзаца между обзором WebSocket/SignalR и конкретной проблемой системы отслеживания задач.
6. Отдельно описать ограничение по задержке межузловой доставки: даже несколько миллисекунд являются не нулевой задержкой, поэтому для предметной области нужно объяснить допустимость такого уровня задержки или честно вынести это в ограничения.
7. Рассмотреть, нужен ли в промышленном варианте механизм подтверждения доставки/блокировки нового состояния до подтверждения от экземпляров, и если нет, явно объяснить, почему для UI-событий системы отслеживания задач выбран более простой transient-подход.

## 3. Укрепление инженерной доказательной базы

1. Провести серию `THESIS_ITERATIONS=30` или `THESIS_ITERATIONS=50` в режиме с Redis backplane и сохранить агрегированные метрики.
2. Добавить сценарий с несколькими клиентами, подписанными на одну группу отчета, чтобы подтвердить доставку группе, а не только одному второму соединению.
3. Зафиксировать негативный сценарий без backplane в отдельном лог-файле или фрагменте приложения: timeout должен быть воспроизводимым и объясненным.
4. Проверить сценарий через единую nginx-точку входа, чтобы доказать не только прямые подключения к `7771`/`7772`, но и работу через балансировщик.
5. Добавить таблицу рисков и ограничений: Redis как зависимость, потеря transient событий при полном сбое, необходимость rejoin после reconnect, границы локального эксперимента.
6. Усилить программную часть, чтобы работа не выглядела только как DevOps-упражнение: подробнее показать код хаба, диагностического метода, клиента проверки, обработку переподключения и логику повторного вступления в группу.

## 4. Улучшение реализации в целевом проекте

1. Проверить, что конфигурация `REDIS_CONNECTION_STRING` документирована в README проекта или backend-сервиса.
2. Убедиться, что диагностический метод хаба не раскрывает лишние данные и подходит только для стенда/отладки.
3. Добавить короткое описание режимов `delivery`, `rejoin`, `failover`, `all` рядом со скриптом `scripts/realtime-scaleout-check.mjs`.
4. Проверить, что Docker Compose стенд поднимается с чистого состояния и не требует неявных локальных переменных.
5. При необходимости добавить smoke-команду, которая запускает health-check nginx и один delivery-сценарий подряд.
6. Подготовить фрагменты кода, которые явно демонстрируют навыки программирования: серверный диагностический API, клиентский сценарий проверки, обработку событий и повторную подписку.

## 5. Визуальные материалы и приложения

1. Обновить три основные схемы: исходная single-node архитектура, целевая multi-instance архитектура, поток события между узлами.
2. Добавить отдельную схему негативного режима без backplane, чтобы визуально показать фрагментацию групп по узлам.
3. На диаграммах явно отметить компоненты, относящиеся к личному вкладу: настройку SignalR backplane, диагностический метод, проверочный клиент, compose/nginx стенд и сценарии испытаний.
4. Добавить формы интерфейса реальной системы, для которой выполнялась работа, чтобы показать практическую значимость и связь real-time контура с пользовательскими сценариями.
5. В приложения вынести только проверяемые фрагменты: compose, nginx upstream, подключение Redis backplane, diagnostics метода хаба, проверочного клиента и результатов запусков.
6. Проверить, что каждый рисунок и каждая таблица упоминаются в тексте до их появления.

## 6. Библиография и ссылки

1. Проверить список источников по ГОСТ Р 7.0.100-2018.
2. Сохранить баланс: не менее 15 источников, интернет-источников не более 50 процентов, иностранных источников не более 50 процентов.
3. Добавить ссылки в текст на все источники из списка, чтобы не осталось источников без цитирования.
4. Для официальной документации Microsoft, Redis и nginx указать актуальные даты обращения.

## 7. Финальная сборка и защита

1. Пересобрать `vkr-draft-1.docx` и `practice-report-draft-1.docx` из исходников.
2. Выполнить render-QA DOCX в PNG/PDF и проверить титульные листы, содержание, рисунки, таблицы и переносы страниц.
3. Обновить презентацию ВКР так, чтобы она рассказывала историю: проблема single-node, выбранная архитектура, реализация, стенд, результаты, ограничения.
4. Подготовить текст доклада на 5-7 минут и список ожидаемых вопросов по Redis backplane, отказоустойчивости, задержкам и границам эксперимента.
